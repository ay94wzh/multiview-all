# policy_robosuite — MultiView Policy for robomimic Tasks (Lift / Can / Square)

Faithful port of the [multiview](../multiview) policy (view-aware temporal shared
encoder, FiLM/Plücker conditioning, diffusion + ACT action heads, online
distillation to a held-out view) to robosuite 1.5.2 robomimic tasks.

**Research question** (unchanged from multiview): can a policy trained on 4 fixed
cameras (top / left / right / bottom) perform well from 1 novel camera (front), by
being explicitly conditioned on camera geometry (Plücker ray maps) instead of
memorizing views?

**Environment:** robosuite 1.5.2 (local clone, `../robosuite`) · tasks Lift, Can,
Square · PyTorch.

The architecture, data pipeline, window semantics, trainer recipe, aux losses,
view dropout and distillation are **identical** to `multiview` — only the env
coupling changed (`envs/robosuite_env.py`, `eval/rollout.py`). All model /
geometry / training / dataset code is verbatim.

---

## 1. What changed vs `multiview`

| | multiview (ManiSkill) | policy_robosuite (robosuite) |
|---|---|---|
| Tasks | PickCube-v1, PushCube-v1 | Lift, Can, Square |
| Robot obs | 9-dim qpos (7 joints + 2 gripper) | 7-dim `robot0_joint_pos` (Panda, no gripper fingers in qpos) |
| Goal | `obs["extra"]["goal_pos"]` (dynamic per step) | `get_goal_pos(env)` — **static per episode** |
| `proprio_dim` | 9 | **7** |
| `trajectory.window_steps` | 64 | **24** (robomimic episodes are 59–127 steps; the old 64 rejected most Lift demos) |
| Cameras | fixed 4+1 in ManiSkill scene | injected into the MuJoCo model via `edit_model_xml` override (same rig as the demo replay) |
| `env.reset()` | returns `(obs, info)`, takes `seed=` | returns `obs` only; **no seed kwarg** — seed `np.random` before reset |
| `env.step()` | 5-tuple | 4-tuple; `done` is horizon-only (`ignore_done=True`) — success via `env._check_success()` |
| `env.action_space` | exists | **does not exist** — use `env.action_dim` |
| Frames | top-down renders | `IMAGE_CONVENTION="opengl"` → **`np.flipud`** in `get_view_rgbs` |
| Gripper | −1 open, +1 close (ManiSkill) | **same sign** in robosuite — demos stored verbatim, rollout snap sign-preserving |
| Human viewer | `env.render_human()` | none (offscreen envs) — render flag ignored |

### Camera rig (identical to `script_robosuite_demos`)

Five fixed cameras on a sphere of radius 1.0 m around the tabletop look target
`(0, 0, 0.8)`, fovy 60°, 160×160 — the same spherical angles as multiview's
`_CAMERA_SPHERICAL`:

| view | azimuth | elevation |
|---|---|---|
| top_camera | 0° | 45° |
| left_camera | 40° | 20° |
| right_camera | −40° | 20° |
| bottom_camera | 0° | 5° |
| front_camera (held-out) | 0° | 30° |

`top/left/right/bottom` are the training views; `front` is never seen at
train time and used by the student at eval.

### goal_pos per task (static within an episode)

- **Lift** → current cube body position (`sim.data.body_xpos[env.cube_body_id]`)
- **Can** → goal-bin center (`env.bin2_pos`)
- **Square** → midpoint of the two pegs (`peg1_body_id` / `peg2_body_id`); the
  actual goal is *which* peg the nut goes on, so the midpoint is a static
  approximation (documented limitation; the single-nut variant is
  `single_object_mode=2`).

Same sources as the demo replay (`script_robosuite_demos/replay_robomimic.py`),
so train and eval conditioning vectors are bit-identical per seed.

## 2. Install

```bash
conda create -n multiview-robosuite --clone know_your_camera -y
conda run -n multiview-robosuite pip install "mujoco<3.10"   # robosuite's cap is load-bearing
conda run -n multiview-robosuite pip install ./robosuite      # local 1.5.2 clone (REGULAR install, not editable)
conda run -n multiview-robosuite pip install ./policy_robosuite
```

> **Do not `pip install -e` the repo-root packages.** Repo-root directories that
> shadow package names (here: none for `policy_robosuite`, but `robosuite/`
> shadows the real package if the repo root is on `sys.path`) take precedence
> over pip's editable finder. Regular installs are required.

## 3. Data

The demos live in `demos/<Task>/episode_XXXXX.npz`, generated by
`../script_robosuite_demos/replay_robomimic.py` (replay of the robomimic PH
hdf5 through robosuite with this rig, 50 demos/task). Each npz has the
**identical schema** as multiview's `collect_data.py`:

```
qpos:      (T, 7)    robot joint positions, one row per action (captured before it runs)
ee_pose:   (T+1, 7)  xyz + wxyz quaternion (site frame), incl. the initial state
actions:   (T, 7)    OSC_POSE world-frame delta actions (3 pos + 3 rot + 1 gripper)
goal_pos:  (3,)      static per task (see above)
success:   (1,)
<view>/rgb  (T+1, 160, 160, 3) uint8, top-down (flipud applied)
<view>/K, <view>/R, <view>/t   camera intrinsics/extrinsics (CV convention)
```

## 4. Training

```bash
conda run -n multiview-robosuite python scripts/train.py --config configs/train_multiview.yaml
```

Three configs, all 100 epochs / 50 demos / image 160 / obs_horizon 3 /
batch 16 / AdamW (groups lr 1e-4, backbone 1e-5) / grad_clip 1.0 / no EMA:

| config | arch | action head | notes |
|---|---|---|---|
| `train_multiview.yaml` | multiview | diffusion (1D-UNet, horizon 16) | teacher + aux + student + distillation |
| `train_baseline.yaml` | baseline | diffusion (same head) | controlled comparison: no FiLM, no fusion, no distillation |
| `train_act_baseline.yaml` | baseline | ACT (CVAE transformer, horizon 30) | transformer-head variant of the baseline |

Checkpoint dirs are separate per config (`checkpoints/`,
`checkpoints_baseline/`, `checkpoints_act_baseline_lift_100_30/`); the
`_shape_signature` check makes cross-config resumption fail loudly.

## 5. Evaluation

```bash
conda run -n multiview-robosuite python scripts/eval.py --config configs/eval.yaml
```

Chunked execution with median temporal ensembling, gripper snap to ±1,
replan every `obs_horizon` steps, success via `env._check_success()`
(`eval.yaml` `use_teacher: false` → the held-out-front-camera student).
